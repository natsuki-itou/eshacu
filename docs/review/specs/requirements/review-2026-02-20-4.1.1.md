# 4.1.1 機能要件一覧レビュー（2026-02-20）

- レビュー対象: `docs/specs/requirements/requirements-definition.md`
- 対象範囲: `4.1.1 機能要件一覧`（表形式化後）

## 指摘事項（優先度順）

### High

1. `対応業務ID` が `TBD` のまま残っており、トレーサビリティが未完成
- 根拠: `1.3`, `6.1`, `6.1.1`, `6.1.2`, `6.1.3`, `6.1.4` の `対応業務ID` が `TBD`。
- 参照: `docs/specs/requirements/requirements-definition.md:121`, `docs/specs/requirements/requirements-definition.md:176`, `docs/specs/requirements/requirements-definition.md:177`, `docs/specs/requirements/requirements-definition.md:178`, `docs/specs/requirements/requirements-definition.md:179`, `docs/specs/requirements/requirements-definition.md:180`
- 影響: 受入観点・設計・テストケースへの紐づけが確定できず、要件抜けの検知が困難。
- 対応案: 業務一覧に該当業務を追加するか、既存業務IDへ確定マッピングするまで `Draft` 扱いを明記する。

2. 認証機能と横断検索機能が業務一覧（3.1）に存在せず、上位要件との整合が取れていない
- 根拠: 業務一覧の業務IDは `BIZ-PROF-*`, `BIZ-POST-*`, `BIZ-PROJ-*`, `BIZ-TAG-*`, `BIZ-VIEW-*` のみで、認証・横断検索に対応する業務IDがない。
- 参照: `docs/specs/requirements/requirements-definition.md:56`, `docs/specs/requirements/requirements-definition.md:80`, `docs/specs/requirements/requirements-definition.md:168`, `docs/specs/requirements/requirements-definition.md:169`
- 影響: 4.1.1 で定義した機能の正当性を業務要件側から説明できず、レビューで再指摘される可能性が高い。
- 対応案: 3.1 に認証/横断検索の業務IDを追加し、4.1.1 の `TBD` を解消する。

### Medium

3. 機能分類番号と章番号が同じ表記で併存し、参照時に解釈がぶれる
- 根拠: セクション見出しが `4.1.1` で、機能分類番号にも `4.1.1`（プロフィール更新機能）が存在する。
- 参照: `docs/specs/requirements/requirements-definition.md:104`, `docs/specs/requirements/requirements-definition.md:167`
- 影響: コメントや課題票で「4.1.1修正」のような記述が曖昧になり、コミュニケーションコストが上がる。
- 対応案: 機能分類番号に接頭辞（例: `F-4.1.1`）を導入するか、参照ルールを文書冒頭で明確化する。

4. 親機能行と子機能行の両方に業務IDを割り当てており、テスト観点の粒度が不揃い
- 根拠: 例として `1.1`（親）と `1.1.x`（子）に同系統の業務IDが重複して記載されている。
- 参照: `docs/specs/requirements/requirements-definition.md:104`, `docs/specs/requirements/requirements-definition.md:105`, `docs/specs/requirements/requirements-definition.md:113`
- 影響: テストケースや設計トレースで「どの粒度を正とするか」が不明確になり、重複作業が発生しやすい。
- 対応案: 「親は分類説明のみ（業務IDなし）」または「業務IDは葉（末端）機能のみ」に統一する。

### Low

5. 公開一覧系の操作要件（ソート/ページング/追加フィルタ）の明示が不足
- 根拠: 公開記事/成果物一覧にはタグ別機能はあるが、一覧操作要件の機能名は定義されていない。
- 参照: `docs/specs/requirements/requirements-definition.md:115`, `docs/specs/requirements/requirements-definition.md:116`, `docs/specs/requirements/requirements-definition.md:118`, `docs/specs/requirements/requirements-definition.md:119`
- 影響: 画面要件・API要件で後追い記載となり、要件トレースが弱くなる。
- 対応案: 操作要件を機能名として追加するか、機能概要に最低限の操作ルールを明記する。

## まとめ

- 表形式化により、機能一覧の可読性と業務ID連携の土台は改善されている。
- 一方で `TBD` 残件と 3.1 との未整合が主要リスクであり、ここを先に解消すると要件の完成度が大きく上がる。

## 取り込み結果（2026-02-20）

- 反映先: `docs/specs/requirements/requirements-definition.md`
- High-1 対応: `1.3` と `6.1.x` の `対応業務ID` の `TBD` を解消。
- High-2 対応: `3.1 業務一覧` に `BIZ-VIEW-007` と `BIZ-AUTH-001`〜`BIZ-AUTH-004` を追加し、4.1.1 と整合。
- Medium-3 対応: `4.1.1` 冒頭に「章番号と機能分類番号の参照ルール」を明記。
- Medium-4 対応: `対応業務ID` を葉（末端）機能のみ記載へ統一し、親機能は `-` に統一。
- Low-5 対応: `1.1.4` と `1.1.6` の機能概要に、ソート/ページング/追加フィルタを明記。

## 再レビュー結果（2026-02-20）

### 指摘事項（優先度順）

### Medium

1. 「葉（末端）機能のみ業務ID記載」ルールにより、一覧表示機能の業務トレーサビリティが一部欠落している
- 根拠: `1.1.4`, `1.1.6`, `2.1.3`, `3.1.3` は一覧表示という独立した機能概要を持つが、子機能が存在するため `対応業務ID` が `-` になっている。
- 参照: `docs/specs/requirements/requirements-definition.md:115`, `docs/specs/requirements/requirements-definition.md:118`, `docs/specs/requirements/requirements-definition.md:129`, `docs/specs/requirements/requirements-definition.md:151`
- 影響: 一覧表示機能（特に `1.1.4` / `1.1.6` に追記したソート・ページング・追加フィルタ要件）が、業務IDと直接結び付かず受入観点に落とし込みづらい。
- 対応案: 次のいずれかに統一する。  
  - 親機能にも業務ID記載を許可する。  
  - 一覧表示の本体を葉機能として分割し、親機能は純粋なグルーピングに限定する。

### 総括

- 前回の High 指摘（`TBD`、3.1 との未整合）は解消済み。
- 現時点の主要残課題は、業務ID付与ルールと機能分解粒度の整合のみ。
